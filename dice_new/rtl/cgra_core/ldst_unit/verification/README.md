# TCU UVM Testbench Documentation

This README documents the UVM testbench for the Temporal Coalescing Unit (TCU) in `rtl/cgra_core/ldst_unit/verification`. It covers how input vectors are generated, how outputs are compared against expected results, and the current verification status.

## Testbench Overview

The testbench is a standard UVM environment with the following components:

- **Interface**: `tcu_if.sv` defines input and output command channels and modports for driver/monitor.
- **Sequence items**: `tcu_seq_item.svh` for input commands, `tcu_out_item.svh` for coalesced outputs.
- **Agent**: `tcu_agent.svh` encapsulates driver, sequencer, and monitor.
- **Driver**: `tcu_driver.svh` performs valid/ready handshakes and drives input commands.
- **Monitor**: `tcu_monitor.svh` captures input/output transactions and publishes analysis ports.
- **Scoreboard**: `tcu_scoreboard.svh` contains the reference model and compares expected vs actual outputs.
- **Sequences**: `tcu_random_seq.svh` provides random and directed traffic patterns.
- **Environment/Test**: `tcu_env.svh` and `tcu_base_test.svh` build, connect, and run sequences.
- **Top**: `tcu_tb_top.sv` instantiates the DUT, interface, clock/reset, and runs the test.

## Input Vector Generation

Input vectors are generated by sequences in `tcu_random_seq.svh` and are driven by the sequencer/driver pipeline:

1. **Directed sequences**
   - **`tcu_coalesce_seq`**: produces multiple writes/reads that share the same cache line and base TID to force coalescing.
   - **`tcu_no_coalesce_seq`**: varies block IDs, write_enable, and base TID regions to prevent coalescing.

2. **Random sequence**
   - **`tcu_random_seq`**: creates randomized `tcu_seq_item` transactions using built-in constraints:
     - Size encoding (1/2/4/8 bytes)
     - Address alignment by size
     - Read vs write mask constraints

The base test (`tcu_base_test.svh`) runs coalescing, non-coalescing, and randomized sequences in order.

## Expected vs Actual Output Comparison

Comparison logic is implemented in `tcu_scoreboard.svh`:

- **Reference model**: coalesces input transactions into a buffer based on base address, block ID, base TID, write_enable, and (for reads) destination register.
- **Flush policy**:
  - Immediate flush if no coalescable input arrives in a cycle.
  - Timeout flush after `MAX_COALESCE_INTERVAL` cycles.
- **Expected outputs** are queued and compared against **actual outputs** captured by the monitor.
- **Comparison checks** include block_id, base_tid, tid_bitmap, address, and write_enable.
- **Sanity checks** validate tid_bitmap non-zero, cache-line alignment, and write mask conditions.

## Coverage

There is **no explicit functional coverage** implementation in the current testbench.

Current coverage is implicit via:
- Directed sequences targeting coalescing and non-coalescing behaviors
- Random traffic exercising legal transaction space
- Scoreboard statistics for inputs/outputs and coalescing ratio

## How To Run (Example)

This repository already includes `filelist.f`. A typical flow is:

1. Compile
2. Run `simv`
3. Inspect `uvm_test.log` and scoreboard summary, waveforms are generate in `tcu_tb.vcd`

Each command below is a single line suitable for `tcsh`:

Compile:

```tcsh
vcs -full64 -sverilog -ntb_opts uvm -timescale=1ns/1ps -debug_access+all -kdb -f filelist.f -l compile.log -o simv
```

Run:

```tcsh
./simv +UVM_TESTNAME=tcu_base_test -l run.log
```
